Tutorial

Some interactive patterns appear on website after website: sections of a page that open and close, tabs that switch between panels of content, and search boxes that filter a list as you type. In this lesson you will build all three, using the skills from the last four lessons. Just as importantly, you will make sure each one works for keyboard and screen reader users, which is where many real-world components fall short.

The starter code contains a help page for students, with frequently asked questions, information about each campus and a glossary of terms. As before, complete each Try It section in the editor before moving on.


The Principles

Every component in this lesson follows the same three principles:

  • Keep the state in JavaScript. Store what is open, selected or typed in variables or on the elements themselves, and update the page from it, as you did in Lessons 6 and 9.
  • Let CSS handle the look. JavaScript adds and removes classes and attributes, and the stylesheet decides what they look like.
  • Tell assistive technology what is happening. A sighted user can see that a section has opened. A screen reader user needs to be told, using HTML attributes designed for exactly this.

ARIA Attributes

ARIA (Accessible Rich Internet Applications) is a set of HTML attributes that describe the state of interactive components to assistive technology. You met one in the CSS unit, aria-current, on the current page's navigation link. This lesson uses two more:

  • aria-expanded is set on a button that opens and closes something. Its value is "true" when the content is open, and "false" when it is closed. Screen readers announce it, for example as "Delivery times, button, collapsed".
  • aria-controls gives the ID of the element that the button opens and closes, connecting the two.
⚠️ Warning: ARIA only describes the state: it does not change it. If you set aria-expanded="true" but do not actually show the content, the screen reader gives users wrong information, which is worse than giving none. Whenever your JavaScript changes what is shown, it must update the ARIA attributes at the same time.

Showing and Hiding: the hidden Attribute

The HTML hidden attribute hides an element completely, just like display: none. It is a Boolean attribute, and JavaScript can turn it on and off with the element's hidden property:

panel.hidden = true;    // hide it
panel.hidden = false;   // show it
⚠️ Warning: The hidden attribute works through one of the browser's default styles, which sets display: none. Any CSS rule of your own that sets display on the same element, such as display: flex, overrides it and the element stays visible. If hidden does not seem to work, check the element's display in your CSS.

Accordions

An accordion is a list of headings, each of which opens and closes a section of content below it. Accordions are often used for frequently asked questions, since they let users scan the questions and open only the ones they need.

Each question in the starter HTML is built like this:

<h3>
    <button type="button" class="accordion-button" aria-expanded="false" aria-controls="answer-1">
        When does term start?
    </button>
</h3>
<div class="accordion-panel" id="answer-1" hidden>
    <p>Term starts on Monday 21 September.</p>
</div>
  • The question is a real <button>, so it can be reached with Tab and pressed with Enter or Space.
  • The button is inside a heading, so screen reader users can still jump between the questions using headings.
  • aria-controls connects the button to its answer, and each answer starts hidden.

To open or close one answer, the JavaScript needs to do three things when its button is clicked: work out whether it is currently open, find its panel, and flip both the panel and the ARIA attribute:

function toggleAccordion(button) {
    const isOpen = button.getAttribute("aria-expanded") === "true";
    const panel = document.querySelector(`#${button.getAttribute("aria-controls")}`);

    button.setAttribute("aria-expanded", String(!isOpen));
    panel.hidden = isOpen;
}
  • ARIA attribute values are always the strings "true" and "false", not booleans, so the code compares with the string "true", and converts back with String().
  • The panel's ID is read from aria-controls, and a # is added in front to make a selector.
  • If the section was open, the panel is now hidden, and if it was closed, the panel is now shown, so panel.hidden is simply set to isOpen.

Try It

  1. In the JS tab, add the toggleAccordion function from the example above.
  2. Select every .accordion-button with querySelectorAll, and use forEach to add a click listener to each one that calls toggleAccordion(button).
  3. Open and close each question in the preview. The starter CSS rotates the arrow on each button whenever its aria-expanded is "true", so the visual style always matches the ARIA state.
  4. Press Tab to reach a question, then press Enter to open it, to check that the accordion works with a keyboard.
💡 Tip: Styling with an attribute selector, such as .accordion-button[aria-expanded="true"], rather than a separate class, means the visual state and the accessible state can never disagree: if one is right, the other is too.
ℹ️ Info: HTML also has a built-in accordion: the <details> and <summary> elements, which open and close with no JavaScript at all. For a simple list of questions, it is often the best choice. Building one yourself, as here, teaches the pattern that many other components use, and gives you full control over how it behaves.

Tabs

Tabs show one panel of content at a time, with a row of buttons to switch between them. Unlike an accordion, exactly one panel is always open.

Tabs use a few more ARIA attributes, which are already written in the starter HTML:

  • role="tablist" on the element containing the buttons, role="tab" on each button, and role="tabpanel" on each panel. A role tells assistive technology what kind of component an element is part of.
  • aria-selected on each tab: "true" for the current tab, and "false" for the others.
  • aria-controls on each tab, giving the ID of its panel.

Tabs are a good example of keeping the state in one variable, and updating everything from it:

const tabs = document.querySelectorAll('[role="tab"]');

function selectTab(selectedTab) {
    tabs.forEach((tab) => {
        const isSelected = tab === selectedTab;
        const panel = document.querySelector(`#${tab.getAttribute("aria-controls")}`);

        tab.setAttribute("aria-selected", String(isSelected));
        panel.hidden = !isSelected;
    });
}

Rather than working out which tab to close, this goes through every tab, and sets each one to selected or not, depending on whether it is the one that was clicked. This is simpler and more reliable: however the tabs were set before, they always end up correct.

Try It

  1. Add the selectTab function from the example above, and a click listener on each tab that calls selectTab(tab).
  2. Click each campus tab, and check that exactly one panel is shown at a time, and the selected tab is highlighted.
ℹ️ Info: The full accessible pattern for tabs also lets users move between tabs with the left and right arrow keys. You can add this with a keydown listener, as an extension: when event.key is "ArrowRight", select the next tab and move focus to it with .focus().

Live Filtering

A search box that filters a list as the user types makes long lists far easier to use. It combines the input event from Lesson 6 with the string methods from Lesson 2:

  1. Each time the search text changes, read it.
  2. For every item in the list, check whether its text includes the search text.
  3. Show the items that match, and hide the rest.

To make the search ignore capital letters, convert both the search text and each item's text to lowercase before comparing them, so that html, HTML and Html all match:

const searchInput = document.querySelector("#glossary-search");
const terms = document.querySelectorAll(".glossary li");

searchInput.addEventListener("input", () => {
    const searchText = searchInput.value.trim().toLowerCase();

    terms.forEach((term) => {
        const matches = term.textContent.toLowerCase().includes(searchText);
        term.hidden = !matches;
    });
});

Every string includes the empty string, so when the search box is empty, every item matches and the full list is shown.

Try It

  1. Add the live filter from the example above, and type into the glossary search box in the preview.
  2. Inside the listener, count the matching terms. Declare let count = 0; before the forEach, and add 1 to it whenever a term matches.
  3. After the forEach, display Showing [count] of [total] terms in the #glossary-count element, using terms.length for the total.
  4. When the count is 0, show the hidden #no-results message, by setting its hidden property to false. Hide it again otherwise.

Announcing Changes

When the list changes as the user types, a sighted user can see the results changing. A screen reader user cannot. The aria-live attribute fixes this: when the text inside an element with aria-live="polite" changes, screen readers announce the new text as soon as the user pauses, without moving their focus away from the search box.

The #glossary-count element in the starter HTML already has aria-live="polite", so every time your code updates the count, a screen reader user hears "Showing 3 of 12 terms".

💡 Tip: Use aria-live sparingly, only for short messages that the user needs to know about, such as a count of results or a confirmation. Announcing every small change quickly becomes overwhelming.

Check Your Page

Your filter should be similar to this:

searchInput.addEventListener("input", () => {
    const searchText = searchInput.value.trim().toLowerCase();
    let count = 0;

    terms.forEach((term) => {
        const matches = term.textContent.toLowerCase().includes(searchText);
        term.hidden = !matches;

        if (matches) {
            count++;
        }
    });

    document.querySelector("#glossary-count").textContent = `Showing ${count} of ${terms.length} terms`;
    document.querySelector("#no-results").hidden = count !== 0;
});

Also check that:

  • Each question opens and closes, and its arrow rotates, using both the mouse and the keyboard.
  • Exactly one campus panel is shown at a time.
  • The glossary search ignores capital letters, and shows the no-results message when nothing matches.

  • Why are ARIA values compared with the string "true" rather than the boolean true?
  • Why does selectTab update every tab, rather than only the one that was clicked?
  • Why must both the search text and the item text be converted to lowercase?
  • What does aria-live="polite" do?
