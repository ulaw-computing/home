Tutorial

Until now, almost every line of your JavaScript has finished its work immediately, before the next line started. But some tasks take time: fetching data from a server on the other side of the world might take a second or more. If JavaScript simply stopped and waited, the whole page would freeze: buttons would not respond, and nothing could be scrolled or typed. In this lesson you will learn how JavaScript handles tasks that take time without freezing the page, using promises, async and await. These are the foundation of fetching data, which starts in the next lesson.

So that you can see exactly what is happening, this lesson uses a simulated request: a function that pretends to fetch weather data, taking two seconds to respond. The starter code contains a weather page and this function. Keep the console open, and complete each Try It section in the editor before moving on.


Synchronous and Asynchronous Code

Synchronous code runs one statement at a time, in order. Each statement must finish before the next one starts:

console.log("First");
console.log("Second");
console.log("Third");

Asynchronous code starts a task, and then carries on with the next statements without waiting for the task to finish. When the task finishes, some code runs to deal with the result. You have seen this already, with setTimeout in JavaScript lesson 4:

console.log("First");

setTimeout(() => {
    console.log("Second");
}, 2000);

console.log("Third");

This logs First, then Third straight away, then Second two seconds later. setTimeout starts the timer and immediately returns, so the script continues while the timer runs in the background.

This is how the page stays responsive. JavaScript in the browser can only do one thing at a time, so instead of waiting for slow tasks, it hands them to the browser, carries on, and comes back to the result later.

The Problem With Waiting

The starter code contains a function called fakeFetchWeather(city). It works like a real request to a weather server: it takes two seconds, and then provides the weather for a city.

Because it is asynchronous, you cannot simply use its result on the next line:

const weather = fakeFetchWeather("Leeds");
console.log(weather);

The console does not show weather data. It shows Promise {<pending>}. The data does not exist yet, so the function cannot return it. Instead, it returns a promise.

Promises

A promise is an object that stands for a result that is not ready yet. Think of the ticket you are given when you order food at a counter: you do not have the food yet, but the ticket promises that you will get it, or be told that something went wrong.

A promise is always in one of three states:

  • Pending: the task has not finished yet.
  • Fulfilled: the task finished successfully, and the promise now holds its result.
  • Rejected: the task failed, and the promise now holds the reason why.

Once a promise is fulfilled or rejected, it is settled, and never changes again.

Using a Promise With then

A promise's then() method takes a callback, which runs when the promise is fulfilled, and is given the result. Its catch() method takes a callback that runs if the promise is rejected:

fakeFetchWeather("Leeds")
    .then((weather) => {
        console.log(`${weather.city}: ${weather.temperature}°C`);
    })
    .catch(() => {
        console.log("The weather could not be loaded.");
    });

This works, but when several tasks depend on each other, such as fetching a city, then its forecast, then a map, the callbacks start to nest and the code becomes hard to read. Modern JavaScript has a cleaner way to write the same thing.


async and await

The await keyword waits for a promise to settle, and then gives you its result, as if the code were synchronous:

async function showWeather() {
    const weather = await fakeFetchWeather("Leeds");
    console.log(`${weather.city}: ${weather.temperature}°C`);
}

showWeather();

Read await as "wait here until this promise has a result". The next line only runs once the weather has arrived, and weather holds the actual data, not a promise.

  • await can only be used inside a function declared with the async keyword.
  • Only the async function waits. The rest of the page, and any code after the call to showWeather(), carries on straight away, so the page never freezes.
  • An async function always returns a promise itself, so code that calls it can also await it.
⚠️ Warning: In this platform, as on most simple web pages, await cannot be used on its own at the top level of your script, outside a function. Always put it inside an async function, and call that function.
ℹ️ Info: async works with arrow functions too: const showWeather = async () => { ... };. You will see this form in event listeners: button.addEventListener("click", async () => { ... });.

Showing That Something Is Happening

For two seconds, the page shows nothing new, and the user has no way of knowing whether anything is happening. Any task that takes time needs a loading state: something on the page that shows the request has started.

The pattern is simple: show the loading state before the await, and replace it with the result after:

async function showWeather(city) {
    result.textContent = "Loading…";

    const weather = await fakeFetchWeather(city);

    result.textContent = `${weather.city}: ${weather.temperature}°C, ${weather.summary}`;
}

Handling Failure

Real requests fail. The user might lose their connection, the server might be down, or the data asked for might not exist. When a promise is rejected, the await fails, and the rest of the function does not run. Without any handling, the loading message would stay on screen for ever, and the user would never find out what happened.

The try...catch statement from the last lesson handles this. Any rejected promise awaited inside try jumps straight to catch:

async function showWeather(city) {
    result.textContent = "Loading…";

    try {
        const weather = await fakeFetchWeather(city);
        result.textContent = `${weather.city}: ${weather.temperature}°C, ${weather.summary}`;
    } catch (problem) {
        result.textContent = `Sorry, the weather could not be loaded. ${problem.message}`;
    }
}

The catch block can receive the reason the task failed, here called problem. Its message property usually describes what went wrong, so it can be shown to the user, or used to decide what to show.

finally

A finally block runs after the try and catch, whatever happened. It is the right place for tidying up that must always happen, such as re-enabling a button:

button.disabled = true;

try {
    // ...
} catch (problem) {
    // ...
} finally {
    button.disabled = false;
}

Disabling the button while a request is in progress stops the user starting the same request several times by clicking repeatedly.

💡 Tip: For every request, plan what the user sees in three situations: while it is loading, when it succeeds, and when it fails. A page that only plans for success will eventually leave a user staring at a loading message that never ends.

Waiting for Several Tasks

Sometimes you need the results of several tasks. Awaiting them one after another works, but each task only starts once the last one has finished, so three two-second requests take six seconds:

const leeds = await fakeFetchWeather("Leeds");
const york = await fakeFetchWeather("York");
const hull = await fakeFetchWeather("Hull");

When the tasks do not depend on each other, Promise.all() starts them all at once, and waits until every one has finished. It takes an array of promises, and gives back an array of results, in the same order:

const results = await Promise.all([
    fakeFetchWeather("Leeds"),
    fakeFetchWeather("York"),
    fakeFetchWeather("Hull")
]);

console.log(results.length);   // 3, after two seconds in total

If any one of the promises is rejected, Promise.all is rejected too, so it should be inside try...catch like any other await.
