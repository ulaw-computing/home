Tutorial

In JavaScript lesson 5, you were warned never to put text that users type into innerHTML, because of an attack called cross-site scripting. In this lesson you will see that attack happen on a real page, fix it, and learn about the other common security problems that affect front-end code. You will finish by looking at what happens once data leaves the browser and reaches a server and its database, including an attack called SQL injection.

The starter code contains a comment wall for the workshop. It works, but it has several security problems, on purpose. Complete each Try It section in the editor before moving on.


Everything in the Browser Is Public

The most important idea in front-end security is that the user controls the browser. Anyone can view your HTML, CSS and JavaScript, change them with the developer tools, turn JavaScript off, or send requests to your server without using your page at all. This has two consequences, which run through this whole lesson:

  • Nothing in front-end code is secret. Passwords, API keys and private data must never be in it.
  • Nothing the browser checks can be trusted. Validation in the browser helps honest users, but a server must check everything again.

Front-end code still has security responsibilities, though: above all, making sure that data cannot turn into code on your page.


Cross-Site Scripting

Cross-site scripting (XSS) happens when an attacker manages to make their own JavaScript run on someone else's page. Once their code is running, it can do anything your own code can: read what the user types, change the page, show a fake login form, or send the user's data to the attacker's server.

Look at the starter's renderComments function. It builds each comment as a string of HTML, including the name and message that a user typed, and adds it to the page with innerHTML. The browser reads that string as HTML, so if the message contains HTML tags, they become real elements.

Try It

  1. Post a comment with your name, and this message, exactly as written: 
    <img src="x" onerror="document.body.style.background='red'">
  2. The page's background turns red. The message created an image with an address that does not exist, and its onerror attribute ran JavaScript when the image failed to load.
  3. Change any line in the CSS tab, so the preview reloads. The page turns red again, because the comment is saved, and runs every time the comments are displayed.

This harmless example only changes a colour, but the attribute could contain any JavaScript at all. Imagine the comments were stored in a database on a server, as they would be on a real website. Every visitor to the page would run the attacker's code, without doing anything except opening the page. This is called stored XSS, and it is one of the most damaging attacks on the web.

ℹ️ Info: You might expect <script> tags to be the danger. In fact, browsers do not run <script> elements added with innerHTML, which is why attacks use event attributes such as onerror instead. There are many such tricks, which is why blocking particular words or tags never works as a defence.

Fixing XSS: Data Stays as Text

The fix is to make sure that user data is always treated as text, never as HTML. Build the elements with createElement, and put the data into them with textContent, exactly as you have done with API data in this unit:

function createComment(comment) {
    const item = document.createElement("li");
    item.className = "comment";

    const name = document.createElement("p");
    name.className = "comment-name";
    name.textContent = comment.name;

    const message = document.createElement("p");
    message.textContent = comment.message;

    item.append(name, message);
    return item;
}

Whatever a user types, textContent displays it as characters on the screen. An HTML tag in a message appears as text, and nothing in it can ever run.

The same rule applies to data from APIs. An API is someone else's server: if it were ever attacked, or simply returned something unexpected, data from it could contain HTML too. Treat all data from outside your own code as text.

Try It

  1. Add the createComment function above, and change renderComments so that it clears the list with replaceChildren() and appends a comment element for each comment, instead of using innerHTML. For now, leave out the website link.
  2. Check the page is no longer red. The harmful comment is still saved, but its message now appears as harmless text.
  3. Click Reset comments to remove it.
💡 Tip: Occasionally, a page genuinely needs to display HTML from users, such as a comment with bold and italic text. This needs a sanitiser: a well-tested library, such as DOMPurify, that removes everything except a list of safe tags. Never try to write your own.

Unsafe Links

The comment wall lets users link to their own website. A link's address can also cause problems. As well as https: addresses, browsers accept addresses that begin with javascript:, which run code when the link is clicked:

<a href="javascript:alert('This ran your code')">My website</a>

Even when a link is built safely with createElement, setting its href to an address like this creates a link that runs the attacker's code for anyone who clicks it. So addresses from users must be checked. The URL object reads an address and splits it into its parts, and fails if the address is not valid at all, so you can check its protocol, the part before the colon:

function isSafeWebAddress(address) {
    try {
        const url = new URL(address);
        return url.protocol === "https:" || url.protocol === "http:";
    } catch (problem) {
        return false;
    }
}

isSafeWebAddress("https://example.com");          // true
isSafeWebAddress("javascript:alert('Hi')");       // false
isSafeWebAddress("not an address");               // false

This is an example of an allow list: it lists what is allowed, and rejects everything else. Allow lists are much safer than block lists, which try to list everything that is dangerous, and always miss something.

Links that open in a new tab should also have rel="noopener noreferrer". noopener stops the new page from controlling your page through window.opener, and noreferrer stops the browser telling the other site which of your pages the user came from.

ℹ️ Info: In the preview, links are handled by this platform, so a javascript: link would not run here. On a real page, it would.

💡 Tip: Notice that createComment checks the address again, even though the form already checked it. Saved data may have been created before the check existed, or changed by someone outside the form. Checking at the point where data is used is called defence in depth.

Browser Checks Can Be Bypassed

The name and message fields have maxlength attributes, and your website check runs before a comment is posted. These help users, but none of them protect anything:

  • A user can delete the maxlength attribute in the developer tools, and type as much as they like.
  • A user can run their own JavaScript in the console, and push anything they like into the comments.
  • On a real website, the form would send its data to a server. Anyone can send the same request with a tool such as curl, without using the form at all.

So every rule that matters, such as length limits, required fields and allowed values, must be checked again on the server, which is the only place the user cannot control. Front-end validation is for the user's convenience; server-side validation is for security.


Keeping Secrets Out of the Front End

As you learned in lesson 7, anything in your HTML, CSS or JavaScript can be read by anyone, so it must never contain:

  • API keys, passwords, or database connection details.
  • Personal data that only some users should see.
  • "Hidden" features protected only by JavaScript, such as an admin page whose only protection is an if statement checking a password in your code.

The same applies to public repositories on GitHub. Every file you have ever committed, including old versions, stays in the repository's history. If you commit a secret by mistake, deleting the file in a later commit does not remove it. Treat it as stolen: cancel the key or change the password straight away, then create a new one.

Web storage is not private either. As you saw in lesson 4, any script running on your page can read localStorage, including an attacker's script injected with XSS. Do not store passwords, login tokens or personal information in it.


Third-Party Scripts

Many sites load JavaScript from other websites, such as a library from a content delivery network (CDN). Every script you load runs with full access to your page, exactly like your own code. If the site hosting it were attacked, and the file changed, the attacker's code would run on your page.

Subresource Integrity (SRI) protects against this. The integrity attribute holds a hash of the file: a short code calculated from its exact contents. The browser calculates the hash of the file it downloads, and refuses to run it if the two do not match:

<script src="https://cdn.example.com/library@2.1.0/library.min.js"
        integrity="sha384-...the file's hash..."
        crossorigin="anonymous"></script>

You do not calculate the hash yourself: CDNs such as cdnjs and jsDelivr show it alongside each file, ready to copy. crossorigin="anonymous" is required, so that the browser is allowed to check a file from another website.

💡 Tip: Only load scripts you need, from sources you trust, and always use a specific version number in the address. An address for the "latest" version can change at any time, and would then fail its integrity check.

Content Security Policy

A Content Security Policy (CSP) is a second line of defence against XSS. It tells the browser which sources of scripts, styles, images and data the page is allowed to use, and the browser blocks everything else. It can be set by the server, or with a <meta> element in the page's <head>:

<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; img-src 'self' https://covers.openlibrary.org; connect-src 'self' https://api.open-meteo.com">

This policy allows scripts, styles and everything else only from the page's own website ('self'), images also from Open Library's covers, and fetch requests also to Open-Meteo. Crucially, a policy like this also blocks inline JavaScript, including event attributes such as onerror, so the attack from the start of this lesson would have been stopped even before you fixed it.

⚠️ Warning: Do not add a CSP to your code in this editor. To show the preview, this platform places your CSS and JavaScript inside the page, and a policy that blocks inline code would block your own code too. Try it on a page of your own, run through a local web server such as Live Server.

Beyond the Browser: Servers and Databases

On most real websites, data from forms is sent to a server, which stores it in a database, and reads it back to build pages. Your front-end code cannot protect the server, because, as you have seen, anyone can send it requests directly. The server must defend itself. You will look at this in more detail in the next unit, but you should know the most important risks now.


SQL Injection

Most databases are queried with a language called SQL. A server that builds an SQL query by joining strings together, including text that a user typed, has the same problem as innerHTML: data can turn into code. Here is part of a login system on a server, written in JavaScript with Node.js:

// DANGEROUS: never build a query like this
const query = "SELECT * FROM users WHERE email = '" + email + "' AND password = '" + password + "'";

If a user types sam@example.com and a password, the query works as intended. But suppose an attacker types this as the password:

' OR '1'='1

The query becomes:

SELECT * FROM users WHERE email = 'sam@example.com' AND password = '' OR '1'='1'

The quote mark in the input ended the password string early, and the rest became part of the query. Because '1'='1' is always true, the query matches users without checking any password, and the attacker is logged in. Other inputs could read every row in the database, change data, or delete whole tables. This is SQL injection, and it has been behind many of the largest data breaches.

The fix is the same idea as textContent: keep data separate from code. A parameterised query, also called a prepared statement, has placeholders where the data goes, and the data is passed separately. The database always treats it as a value, never as part of the query:

// Safe: the data is passed separately from the query
const query = "SELECT * FROM users WHERE email = ?";
const results = await database.query(query, [email]);

Every server language, including PHP, Python, Java and C#, supports parameterised queries, and they should be used for every query that includes data from outside the code.


Other Server-Side Defences

  • Validate everything on the server, using allow lists: the right type, the right length, and only the allowed values.
  • Encode output. When a server builds HTML that includes stored data, it must convert characters such as < into HTML entities such as &lt;, so that the data displays as text. This is the server's version of textContent, and prevents stored XSS.
  • Never store passwords as plain text. Store a password hash, made with an algorithm designed for passwords, such as bcrypt or Argon2. If the database is stolen, the passwords themselves are not.
  • Give the least privilege. The account a website uses to connect to its database should only be able to do what the website needs. A page that only reads data does not need permission to delete tables.
  • Show users plain messages. Detailed technical messages, such as the text of a failed query, help attackers understand your system. Show users a plain message, and record the details on the server, as you did with failed requests in lesson 6.
  • Limit repeated attempts, such as many wrong passwords in a row, to slow down attackers who try thousands of guesses.

The OWASP Top 10, published by the Open Worldwide Application Security Project at owasp.org, lists the most serious security risks to web applications, with explanations and defences for each. It is the standard reference for web security, and well worth reading.

Check Your Page

Your createComment function should be similar to this:

function createComment(comment) {
    const item = document.createElement("li");
    item.className = "comment";

    const name = document.createElement("p");
    name.className = "comment-name";

    if (comment.website && isSafeWebAddress(comment.website)) {
        const link = document.createElement("a");
        link.href = comment.website;
        link.target = "_blank";
        link.rel = "noopener noreferrer";
        link.textContent = comment.name;
        name.append(link);
    } else {
        name.textContent = comment.name;
    }

    const message = document.createElement("p");
    message.textContent = comment.message;

    item.append(name, message);
    return item;
}

Also check that the comment from the first Try It now appears as plain text, and that unsafe website addresses are rejected with a message.
