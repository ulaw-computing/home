Tutorial

In this final lesson, you will bring together everything from this unit to build a complete page powered by a live API: the UK Weather Explorer, which shows the current weather and a three-day forecast for places around the UK, lets users sort and filter them, shows details in a dialog, and lets users add places of their own.

The HTML is complete, and most of the CSS is written, along with the list of places and the weather descriptions. Your job is the JavaScript, and a few finishing touches to the CSS. As in the consolidation lessons of the previous units, there are no step-by-step instructions: you have a brief, a plan and a checklist. If you are unsure how to do something, look back at the relevant lesson.


The Brief

The page must include the following features.

Loading the Forecast (Lessons 5, 6 and 7)

  • Clicking Load forecast requests the weather for every place in a single request to Open-Meteo, built with URLSearchParams (see the plan below).
  • The request asks for the current temperature, weather code and wind speed, and the daily maximum and minimum temperature and maximum chance of rain, for three days, in UK time.
  • While loading, the spinner is shown, the status says Loading the forecast…, and the button is disabled. After loading, the spinner is hidden and the button is re-enabled with the text Refresh forecast.
  • If the request fails, or the data is not in the shape you expect, the user sees a plain message asking them to try again. The button stays available, so they can.

Displaying the Places (Lessons 6, 7 and 8)

  • Each place is displayed as a card in #place-list, with the class place-card, showing its name in an <h3>, the current temperature in a paragraph with the class temperature, a description of the weather, and paragraphs with the class detail for the wind speed, today's highest and lowest temperatures, and today's chance of rain.
  • Units come from the response's units objects, and any missing value shows a sensible fallback rather than undefined.
  • Each card has a Details button.
  • Cards are created with createElement and textContent, never innerHTML.

Sorting and Filtering (Lesson 8)

  • The Sort by menu sorts the cards in the order the places were added, by name from A to Z, or by current temperature, warmest or coldest first, without changing the original order.
  • The rain checkbox shows only places where today's chance of rain is 50% or more.
  • Sorting and filtering work together, update instantly, and never send a new request.
  • The count says, for example, Showing 4 of 6 places, and says No places match your filter. when nothing matches.

Details Dialog (Lesson 10)

  • Clicking a card's Details button opens #details-dialog as a modal, showing the place's name, its current weather, and a list item in #details-days for each of the three days, with the day's name, such as Monday, its description, its highest and lowest temperatures, and its chance of rain.
  • The dialog closes with its Close button, with Escape, and by clicking the backdrop.

Adding a Place (Lessons 4, 7 and 9)

  • The Add a UK Place form is validated before any request is sent: the name must not be empty, must be between 2 and 50 characters, may contain only letters, spaces, hyphens and apostrophes, and must not already be in the list. Each problem has a clear message, shown with aria-invalid, and focus returns to the field.
  • A valid name is looked up with Open-Meteo's geocoding API (see the plan below). If no UK place is found, the user is told so.
  • A place that is found is added to the list, and the forecast is loaded again so that it appears. While the place is being looked up, the Add place button is disabled.
  • Added places are saved in localStorage, and are still there after the page reloads.

Theme and Motion (Lessons 1, 2, 3 and 4)

  • The theme button switches dark mode on and off, by adding a dark class to the body, with aria-pressed kept up to date. In the CSS, body.dark redefines the custom properties. The choice is saved, and restored when the page loads.
  • Cards lift slightly when hovered, or when their button has focus, using a transform and a transition.
  • The spinner spins, using @keyframes.
  • When the user prefers reduced motion, the cards do not move, and the spinner turns much more slowly.
💡 Tip: These dark-mode colours all pass the WCAG contrast checks: background #121212, surface #1e1e1e, text #eeeeee, muted text #bdbdbd, primary #90caf9, primary dark #bbdefb, text on primary #121212, and error #ef9a9a.

Plan Before You Build

The State

This page has more state than any page so far. Store it in top-level let variables:

let addedPlaces = loadSavedPlaces();                // places the user has added
let places = [...defaultPlaces, ...addedPlaces];    // every place, in the order added
let forecasts = [];                                 // one object per place, after loading

loadSavedPlaces() is your own function, which reads the added places from localStorage, with ?? [] as a fallback. The spread syntax, from lesson 8, joins the two arrays into one. Save only addedPlaces, not the default places, so that the defaults can never be saved twice. When the user adds a place, push it onto both arrays.


One Request for Many Places

Open-Meteo's documentation explains that a single request can include several locations, by giving comma-separated lists of latitudes and longitudes. The map and join methods build these lists:

const params = new URLSearchParams({
    latitude: places.map((place) => place.latitude).join(","),
    longitude: places.map((place) => place.longitude).join(","),
    current: "temperature_2m,weather_code,wind_speed_10m",
    daily: "weather_code,temperature_2m_max,temperature_2m_min,precipitation_probability_max",
    timezone: "Europe/London",
    forecast_days: 3
});

One request for six places is much kinder to the API than six requests. The response is an array, with one object for each location, in the same order as your places. But if only one location is requested, the response is a single object, not an array. Code that handles both is safer:

const locations = Array.isArray(data) ? data : [data];

Each location object has current and current_units objects, as in lesson 7, and daily and daily_units objects. Each property of daily is an array with one value per day: daily.time[0] is today's date, and daily.temperature_2m_max[0] is today's highest temperature. Log a response and explore it before you write the code to display it.

Join each location to its place, so that every forecast knows its place's name:

forecasts = locations.map((location, index) => ({
    place: places[index],
    current: location.current,
    currentUnits: location.current_units,
    daily: location.daily,
    dailyUnits: location.daily_units
}));

The second parameter of the function passed to map is the item's index. The extra round brackets around the curly braces tell JavaScript that the arrow function returns an object, rather than starting a block of code.


Finding a Place

Open-Meteo's geocoding API finds a place's location from its name. Ask for one result, in the UK only:

const params = new URLSearchParams({
    name: placeName,
    count: 1,
    countryCode: "GB"
});
const url = `https://geocoding-api.open-meteo.com/v1/search?${params}`;

The response has a results array, and each result has a name, latitude and longitude. When nothing is found, the results property is missing altogether, so check for it with optional chaining: data.results?.[0] gives the first result, or undefined if there is none. Use the name from the result, rather than what the user typed, so that the capital letters are correct.


Functions

Plan your code as small functions, each with one job. You might have:

  • loadSavedPlaces() and savePlaces() for local storage.
  • buildForecastUrl() and an async function loadForecast(), which handles the loading, success and failure states.
  • createPlaceCard(forecast, index), which builds and returns one card.
  • getVisibleForecasts(), which returns a sorted and filtered copy of forecasts.
  • render(), which clears the list, creates the visible cards, and updates the count.
  • openDetails(forecast), which fills in and opens the dialog.
  • validatePlaceName(name), which returns an error message or an empty string, and an async function findPlace(name), which looks a place up.
  • setDarkMode(isDark), which applies a theme, updates the button and saves the choice.

As in the last unit, every listener follows the same pattern: update the state, then call render(). To find a card's forecast from its Details button, give the button a data-index attribute holding the forecast's position in forecasts, not its position on screen, which changes with sorting and filtering. An array's indexOf method gives an item's position in it: forecasts.indexOf(forecast).

ℹ️ Info: As in the rest of this unit, the forecast loads when the button is clicked, so that the preview does not send a request every time you type. On your own published site, you would call loadForecast() once when the page loads, instead of making the user click.

Build in Stages

Build one feature at a time, and check that it works before starting the next.

  1. The request: build the address, open it in a new tab to check it, then fetch it and log the data.
  2. The forecasts: turn the response into the forecasts array, and log it.
  3. One card, then every card: write createPlaceCard and render.
  4. Loading and failure states: add the spinner, status messages and button changes. Test failure by misspelling a parameter, as in lesson 7.
  5. Sort and filter: write getVisibleForecasts, the count and the listeners.
  6. Details dialog.
  7. Adding places: validation first, then the geocoding request, then saving.
  8. Theme and motion: the dark theme, its saved choice, the card transition and the spinner.
💡 Tip: While you work on stages 5 and 6, you do not need to click Load forecast after every change. Load the forecast once, then use the sort menu and filter: they only use the data already loaded. The preview does reset when you change your code, though, so keep your requests to when you need fresh data.

Debugging Challenge

Each of the snippets below is from a weather page that does not work properly. The problem is described, but not the cause. For each one, find the bug by reading the code carefully. You can check your answer by revealing it.

1. Every temperature says undefined

The cards appear, with the right names and descriptions, but every temperature reads undefined°C.

temperature.textContent = `${forecast.current.temperature}${forecast.currentUnits.temperature_2m}`;
Reveal the answer

The property is called temperature_2m, not temperature. Reading a property that does not exist gives undefined. Always copy property names from the logged data or the documentation, rather than typing them from memory.

2. The failure message always appears

The address works perfectly when opened in a tab, but the page always says the forecast could not be loaded.

const response = await fetch(buildForecastUrl());

if (response.ok) {
    throw new Error(`The request failed with status ${response.status}.`);
}
Reveal the answer

The condition is the wrong way round: it throws an error when the response is OK. It should be if (!response.ok).

3. The data never arrives

The request succeeds, but the page shows the failure message, and logging data shows Promise rather than the forecast.

const data = response.json();
const locations = Array.isArray(data) ? data : [data];
Reveal the answer

response.json() returns a promise, because reading the body takes time. Without await, data is the promise itself, not the data, so reading its properties fails. It should be const data = await response.json();.

4. Sorting changes the Details

After sorting by Warmest first, clicking the first card's Details button shows the details of a different place.

getVisibleForecasts().forEach((forecast, index) => {
    placeList.append(createPlaceCard(forecast, index));
});
Reveal the answer

index here is the card's position in the sorted and filtered array, but the Details button looks the forecast up in the original forecasts array. The button needs the forecast's position in forecasts: createPlaceCard(forecast, forecasts.indexOf(forecast)).

5. A place name appears in bold

A user added a place by typing <b>York</b>. The validation should have rejected it, but it was changed to allow any characters, and now the card shows York in bold.

heading.innerHTML = forecast.place.name;
Reveal the answer

innerHTML treats the name as HTML, so the tags became a real element, and other tags could run code, as you saw in lesson 11. It should be heading.textContent = forecast.place.name;. Validation is a useful extra layer, but displaying data safely must never depend on it.


Extension Challenges

If you finish early, try one or more of these:

  • Remove a place: add a Remove button to the cards of places the user added, with a confirmation dialog, as in lesson 10.
  • Remember the forecast: save the forecast in sessionStorage, with the time it was loaded, and use it instead of a new request if it is less than ten minutes old.

  • Feels like: add the "apparent temperature" to each card, after finding its name in the documentation.

Check Your Page

Your page is complete when:

  • Clicking Load forecast shows the spinner, then a card for each of the six places, using a single request.
  • Misspelling a parameter shows a plain failure message, and the button can be used to try again.
  • Each sort order and the rain filter work, together and separately, and the count is always correct.
  • Each Details button opens the right place's three-day forecast, even after sorting and filtering, and the dialog closes in all three ways.
  • Adding an empty name, a single letter, York!, leeds (already in the list) and Nowhereville each give the right message, and York is added and saved.
  • The theme switches and is remembered, the cards and spinner move, and they stop moving when reduced motion is turned on.
  • Every feature works with the keyboard only, and in a narrow pop-out preview.
  • No data from the API or the user is displayed with innerHTML, and the Open-Meteo credit is in the footer.

Make sure you download your work using the Download button. When you test your downloaded page on your own computer, remember to use a local web server, such as Live Server, as you learned in lesson 6.


Unit Summary

In this unit, you have learned to:

  • Store design values in CSS custom properties, and change a whole theme by redefining them.
  • Use transforms, transitions and keyframe animations where they genuinely help users, and respect their preference for reduced motion.
  • Convert data to and from JSON, and save it in the browser with web storage.
  • Write asynchronous code with promises, async and await, and handle loading, success and failure.
  • Load data with fetch, check responses, and handle both kinds of failed request.
  • Read API documentation, build request addresses, and choose APIs that are suitable for front-end use.
  • Display API data safely and robustly, handling missing values and empty results, and sort and filter it.
  • Validate forms with clear, accessible feedback, and use dialogs to show details and confirm actions.
  • Recognise and prevent common security problems, in the browser and on the server.
